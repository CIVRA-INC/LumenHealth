# Decisions

Durable architecture and product decisions, newest last. Significant ones have a full record in
[`adr/`](adr/). Reverse a decision by adding a new entry that supersedes it, not by editing history.

| #   | Decision                                                                                                                                                                                               | Rationale (short)                                                                                                  | ADR                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| D1  | Greenfield build on `greenfield/foundation`; earlier prototype preserved in git history only.                                                                                                          | The working tree arrived empty of prior code; a clean architecture was the stated goal.                            | [0001](adr/0001-monorepo-modular-monolith.md)               |
| D2  | pnpm monorepo; NestJS modular monolith; React + Vite SPA; no microservices.                                                                                                                            | Solo developer; one deployable; module boundaries enforced by convention and tests.                                | 0001                                                        |
| D3  | Shared contracts as zod schemas in `packages/contracts`, consumed by API and web.                                                                                                                      | One definition of every request shape, permission and state machine; validated at the boundary.                    | [0002](adr/0002-contracts-zod.md)                           |
| D4  | Server-side sessions in an opaque HttpOnly cookie; argon2id; same-origin (Vite proxy / reverse proxy).                                                                                                 | No tokens in browser-accessible storage; revocable; simple CSRF story.                                             | [0003](adr/0003-session-authentication.md)                  |
| D5  | Static role → permission mapping in code (4 roles).                                                                                                                                                    | Easy to reason about and test; custom roles are a later, additive change.                                          | [0004](adr/0004-static-rbac.md)                             |
| D6  | Tenant isolation: app-level org scoping + PostgreSQL RLS + composite foreign keys; two DB roles (owner / app).                                                                                         | Defense in depth: a forgotten filter cannot leak across tenants.                                                   | [0005](adr/0005-tenant-isolation.md)                        |
| D7  | Encounter lifecycle IN_PROGRESS → FINALIZED → CLOSED (+ ENTERED_IN_ERROR); signed content locked by DB trigger; addenda.                                                                               | Distinguishes drafts from the legal record; corrections are explicit and attributable.                             | [0006](adr/0006-encounter-lifecycle.md)                     |
| D8  | UUIDv7 primary keys generated by the application; `version` and `updatedAt` on mutable aggregates.                                                                                                     | Globally unique and time-ordered; safe for a future facility-local node.                                           | [0007](adr/0007-identifiers-and-sync-readiness.md)          |
| D9  | Payments: provider-agnostic billing core; Stellar as an adapter; testnet first; production disabled by default.                                                                                        | Billing must not depend on a rail; no payment is trusted without server-side verification.                         | [0008](adr/0008-payments-boundary.md)                       |
| D10 | Append-only audit table (REVOKE + trigger); metadata never holds clinical content.                                                                                                                     | Healthcare audit requirement; not a blockchain substitute.                                                         | 0005                                                        |
| D11 | The queue is a view over `CHECKED_IN` appointments, not a table.                                                                                                                                       | One source of truth; no sync problem between queue and appointment.                                                | —                                                           |
| D12 | Patients are organisation-wide; appointments, queue, dashboard and encounter history are branch-scoped by access.                                                                                      | Hospital groups share a registry; clinical activity follows the branch the user may work in.                       | 0005                                                        |
| D13 | Default time zone `Africa/Lagos`, configurable per organisation; instants stored UTC; "today" evaluated in org zone.                                                                                   | Target market; avoids server/browser zone bugs.                                                                    | —                                                           |
| D14 | Local dev requires Docker only for PostgreSQL; the apps run on the host.                                                                                                                               | Fast feedback, minimal setup.                                                                                      | —                                                           |
| D15 | _Superseded by D16._ Visual identity "the chart": IBM Plex Sans + Plex Mono for data, one ultramarine accent, hairlines over shadows, status as dot + word. Redesigned session 2.                      | Distinct, calm and data-forward; avoids the generic dashboard look.                                                | —                                                           |
| D16 | Visual identity "Lumen Instrument": warm-stone canvas, evergreen rail, chartreuse as fill only, Fraunces / Instrument Sans / Geist Mono, bundled fonts; all UI built from `packages/ui`.               | Session 2's look was judged generic; a distinct, calm, data-forward identity with one signature motif (day ruler). | [0009](adr/0009-lumen-instrument-and-design-system.md)      |
| D17 | Lists use offset pagination: `page`/`pageSize` (max 100), whitelisted `sort` + `order`, id tiebreak, flat additive response with `totalPages`/`hasNextPage`/`hasPreviousPage`; table state in the URL. | Page-number UX for clinic-scale registries; additive so existing clients keep working; deterministic and testable. | [0010](adr/0010-list-pagination-contract.md)                |
| D18 | Platform administration is a user-level `platformRole`, separate from organisation roles; platform sessions carry no membership or branch; explicit `@RequirePlatformPermissions`.                     | No fake memberships; an organisation role can never confer platform power.                                         | [0011](adr/0011-platform-administration-and-invitations.md) |
| D19 | Onboarding by single-use hashed-token invitations (fragment links, 7-day expiry); no shared temporary passwords for new people.                                                                        | Passwords are never transmitted; tokens are unguessable and not recoverable from the database.                     | 0011                                                        |
| D20 | The first platform administrator is created only by an operator command; no endpoint. Organisations can be suspended (sessions revoked, data kept).                                                    | No remotely reachable way to mint platform power.                                                                  | 0011                                                        |
